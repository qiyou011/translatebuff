## Context

`active-dedup.ts` 目前把 `local:forkActiveTracking` 当作单个 UTC 日期串：命中即当天不再上报。判定里没有任何身份维度，所以换账号、以及「游客 → 登录」都不会重新上报。

`track-active.ts` 的现有顺序是：算日期 → 判去重 → 落标记 → 读会话与配置 → 上报。会话在判定之后才读。

会话形状（`forkSessionSchema`）里可用的稳定字段只有 `phone`（国内线登录必有）与 `email`（海外线 Google 登录必有）；`user` 是宽松 record，形状本身还是未定项；`loginCredential` 每次登录都会变。

## Goals / Non-Goals

**Goals**

- 游客与每个已登录账号各自成为一个去重身份，当天各上报一次。
- 同一账号重新登录不重复上报。
- 去重记录不随账号数无限增长。

**Non-Goals**

- 不改去重的时区与自然日语义（仍是 UTC 自然日）。
- 不改上报报文字段、接口路径、三条翻译通路的接入点。
- 不做旧格式数据迁移。
- 不在登出/清态处清记录——身份分桶已覆盖换号，再清一次只会让同账号重登也重报。

## Decisions

**D1：身份取 `phone || email || loginCredential`，游客固定为 `anon`**

`phone` / `email` 是账号的稳定标识，两条 edition 各有其一，重新登录不变，正好满足「同账号重登不重报」。回落到 `loginCredential` 只为兜住两者皆空的会话——那种情况下宁可多报一次（后端会去重），也不能把不同账号并进同一个桶造成漏报。

不选 `user` 里的 uid：该字段形状在上一个变更里就是未定项，依赖它等于把一个悬而未决的契约变成运行期依赖。

**D2：存储结构改为 `Record<身份, 日期>`，不做向后兼容读取**

读到非对象（旧的裸日期字符串）一律视为无记录。写一个兼容分支的收益只是「升级当天少报一次」，而代价是这个分支要在代码里长期留着——用后端去重吸收这一次重复更划算。

**D3：写入时丢弃非当日条目**

映射的键是账号标识，不限制的话会随设备上登录过的账号数持续增长。在写入处顺手只保留当日条目即可，不需要单独的清理任务或过期扫描。

**D4：`track-active.ts` 调整为「先读会话 → 算身份 → 判去重 → 落标记 → 上报」**

身份来自会话，所以会话必须在去重判定之前读到。顺带的效果是：会话读取失败时会在落标记之前就退出，不再出现「标记已写、事件没发、当天不再重试」的静默丢失——这不是本变更的目标，但顺序调整后自然如此。

## 数据模型 / 接口契约

`local:forkActiveTracking`：

- 旧：`"2026-09-04"`
- 新：`{ "anon": "2026-09-04", "13800000000": "2026-09-04" }`

上报报文、接口路径、请求头一概不变。身份标识只用于本地去重，不进报文。

## Risks & Mitigations

| 风险                         | 应对                                                                              |
| ---------------------------- | --------------------------------------------------------------------------------- |
| 去重桶键含手机号/邮箱（PII） | 这两个字段本就明文存在同扩展的 `forkSession` 里，不新增暴露面；且绝不写进上报报文 |
| 升级当天存量用户可能多报一次 | 后端账号级去重吸收；仅一次性影响                                                  |
| 同设备多账号导致上报量上升   | 这正是账号级口径要的结果，后端去重保证看板不重复计                                |

回滚：把 `active-dedup.ts` 与 `track-active.ts` 恢复到改动前即可。存储键留下的映射值会被旧代码读成非字符串，旧的 `shouldReportOn` 做的是不等比较，结果是「当天重报一次」后恢复原样，无需清数据。
