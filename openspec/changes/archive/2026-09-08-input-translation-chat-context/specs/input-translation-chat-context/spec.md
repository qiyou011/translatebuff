## ADDED Requirements

### Requirement: 按站点登记对话消息选择器

系统必须维护一份「站点 → 对话消息选择器」的登记，用于声明该站点上哪些 DOM 节点属于对话消息。未登记的站点，输入翻译的语言判定行为必须与本次变更前逐字一致，不新增本规格的纠错条或失败 notice。消息内部要剔除的噪音节点必须复用站点规则已有的 `excludeSelector`，不得另立一套。

#### Scenario: 站点已登记对话选择器

- **当** 当前地址命中已登记的站点（如 Discord 频道页）
- **则** 输入翻译在解析「网页源语言」时必须启用对话语言检测

#### Scenario: 同一站点下没有对话的页面

- **当** 当前地址是该站点上没有对话的页面（如 Discord 发现页）
- **则** 必须不启用对话语言检测

#### Scenario: 站点未登记

- **当** 当前地址未命中任何已登记站点，或地址非法
- **则** 输入翻译必须沿用原有的整页源语言逻辑，行为逐字不变

### Requirement: 目标语言跟随最近的对话消息

当输入翻译的语言选项取值为「网页源语言」时，系统必须按最近 5 条对话消息判定语言，并以该语言作为翻译方向的一端。

#### Scenario: 对话为单一语种

- **当** 最近 5 条消息均为俄语
- **则** 系统必须判定为俄语，并将输入内容翻译为俄语

#### Scenario: 对话中途切换语种

- **当** 较早的消息为韩语、最近的消息为日语
- **则** 系统必须优先使用最新消息中的假名或谚文直接判为日语或韩语；其他情况仅合并最近 5 条内与最新消息同文字系统的样本进行本地检测，不让更早的其他文字系统公告覆盖最新对话

#### Scenario: 消息不足 5 条

- **当** 当前对话仅有 2 条消息
- **则** 系统必须使用现有的全部消息进行判定，不得报错

### Requirement: 检测样本必须剔除已知噪音节点

提取消息文本前，系统必须剔除当前站点规则 `excludeSelector` 命中的子孙节点（时间戳、用户名、回复预览等），以免非对话内容干扰语种判定。

#### Scenario: 消息含时间戳与用户名

- **当** 消息节点内部包含「已编辑」时间戳与用户名元素
- **则** 这些元素的文本必须不参与语种判定

#### Scenario: 消息含 @提及或频道链接

- **当** 俄语消息中含有 @提及或频道链接
- **则** 系统仍必须将该消息判定为俄语（提及与频道链接无法剔除，属已知限制，由手动改语言兜底）

### Requirement: 不得覆盖用户显式设定的源语言

仅当全局语言设置中的源语言为「自动」时，才允许启用对话语言检测。用户已将源语言钉死为具体语种时，系统必须直接采用该语种。

#### Scenario: 源语言为自动

- **当** 全局源语言为「自动」且站点声明了聊天上下文选择器
- **则** 系统必须使用对话语言检测结果

#### Scenario: 源语言被用户钉死

- **当** 全局源语言被用户设为「英语」
- **则** 系统必须使用英语，且不得执行对话语言检测

### Requirement: 检测失败时回退整页源语言

当对话语言无法判定时，系统必须回退到原有的整页源语言逻辑，并在界面上标注本次结果来自网页源语言而非自动检测。

#### Scenario: 页面上没有任何消息节点

- **当** 选择器未命中任何节点
- **则** 系统必须回退到整页源语言，且不得报错

#### Scenario: 消息文本过短或无法判定语种

- **当** 最近 5 条消息拼接后不足以判定语种（例如全为表情或链接）
- **则** 系统必须回退到整页源语言，并将界面标注显示为「按网页源语言」

### Requirement: 源语言与目标语言相同时必须给出提示

当解析后的两端语言相同时，系统必须不执行翻译，且必须向用户给出可见提示，不得静默无反应。

#### Scenario: 对话语言与用户目标语言一致

- **当** 对话判定为简体中文，而用户的翻译目标语言也是简体中文
- **则** 系统必须提示「与目标语言相同，未翻译」，且不得替换输入框内容

#### Scenario: 同语言提示结束

- **给定** 系统正在输入框上方显示「与目标语言相同，未翻译」提示
- **当** 用户继续输入、消息实际发送、按 Esc，或焦点真正离开输入框
- **则** 系统必须关闭该提示

### Requirement: 输入框上方提供内联纠正入口

翻译完成并成功替换输入内容后，系统必须在输入框上方显示内联条，展示本次使用的目标语言、该语言的来源，并提供手动改语言与撤销两个操作。

#### Scenario: 自动检测成功

- **当** 对话语言检测成功并完成翻译
- **则** 内联条必须显示该语言并标注「自动检测」

#### Scenario: 回退到整页源语言

- **当** 检测失败并回退
- **则** 内联条必须标注「按网页源语言」而非「自动检测」

#### Scenario: 用户手动改语言

- **当** 用户在内联条中选择另一种语言
- **则** 系统必须以**原始输入文本**重新翻译，并替换输入框内容

#### Scenario: 用户撤销

- **当** 用户点击撤销
- **则** 输入框必须恢复为翻译前的原始文本

#### Scenario: 用户编辑译文后撤销

- **给定** 用户连续按 3 次空格触发翻译，系统已成功替换输入内容并保存触发时的原始文本
- **当** 用户对译文执行删除、修改或新增内容后点击撤销
- **则** 输入框必须恢复为触发翻译前保存的原始文本，不得恢复为任何编辑后的译文或中间状态
- **且** 用户对译文的上述编辑不得改写撤销所使用的原始文本快照，也不得仅因内容发生变化而使内联条消失

#### Scenario: 焦点真正离开后暂时隐藏内联条

- **给定** 翻译成功后内联条正在显示
- **当** 焦点从输入框及内联条交互范围移到外部元素
- **则** 系统必须暂时隐藏内联条，但继续保留该输入框的原始文本快照与会话归属
- **但是** 焦点进入内联条、语言选择器或其弹出菜单不算失焦，内联条必须继续保留

#### Scenario: 重新聚焦原输入框后恢复内联条

- **给定** 翻译内联条因真正失焦而暂时隐藏，且原输入元素仍在文档中
- **当** 用户重新聚焦当初触发翻译的同一个输入框
- **则** 系统必须重新显示该内联条，并继续使用原有的不可变原文快照
- **但是** 聚焦其他输入框不得显示或复用这次会话的内联条

#### Scenario: 消息实际发送后关闭内联条

- **给定** 翻译成功后内联条正在显示
- **当** 用户将当前输入框中的消息实际发送
- **则** 系统必须关闭内联条
- **且** 再次聚焦原输入框时不得恢复本次已结束的内联条
- **但是** 换行或其他未提交消息的按键操作不得关闭内联条

#### Scenario: 按 Esc 关闭内联条

- **给定** 翻译成功后内联条正在显示
- **当** 语言菜单未展开且用户按 Esc
- **则** 系统必须关闭内联条
- **且** 再次聚焦原输入框时不得恢复本次已结束的内联条

#### Scenario: 语言菜单展开时按 Esc

- **给定** 内联条的语言菜单正在展开
- **当** 用户第一次按 Esc
- **则** 系统必须只关闭语言菜单并保留内联条
- **且** 未提交选项且焦点仍在本菜单内时，关闭后焦点必须回到可用的语言按钮；不得因菜单卸载时的焦点空档隐藏条
- **但是** 已在外部输入框、同一 ShadowRoot 的其他控件或仅在 shadow host 上的焦点不得被强行拉回

#### Scenario: 翻译期间用户修改了输入

- **当** 首次翻译返回时输入框内容已被用户改动，系统放弃替换
- **则** 系统必须不显示内联条，以免撤销操作覆盖用户的新输入

#### Scenario: 页面存在多个输入框

- **当** 用户在主输入框翻译后，将焦点切换到另一个输入框
- **则** 原内联条必须隐藏且不得显示到另一个输入框；重新聚焦主输入框时必须恢复
- **且** 撤销必须只作用于当初执行翻译的那个输入框；若该元素已不在文档中，撤销必须不产生任何写入

### Requirement: Discord 翻译失败必须提供分级反馈

系统必须在已登记的 Discord 频道页提供失败反馈，不得静默；不得在其他站点新增此 UI。显式语言配置仍不显示纠错条，但失败 notice 不受该限制。

#### Scenario: 首次翻译失败与重试

- **当** 首次翻译发生网络、超时、限流、服务故障或未知错误
- **则** 必须保留原文，同位置显示「翻译失败」与「重试」，不显示语言选择或撤销
- **且** 重试沿用本次方向而不再次 enableCycle，期间显示「翻译中…」与原有输入框 spinner；成功才显示符合条件的纠错条，失败恢复 notice

#### Scenario: 不可重试的错误

- **当** 错误为内容安全拦截、未登录、套餐限制、额度耗尽或 BYOK 密钥鉴权失败
- **则** 必须仅提供明确说明而不显示重试或登录、升级按钮；已有成功译文的撤销仍可用
- **且** 内容安全说明为「内容未通过安全审核，无法翻译」，其余复用现有文案，不直接展示原始响应正文

#### Scenario: 首次失败后继续编辑

- **给定** 首次失败 notice 正在显示且没有重试请求执行中
- **当** 用户编辑原文、真正失焦、按 Esc 或发送消息
- **则** 必须关闭本次失败 notice；下一次三空格使用新的原文快照
- **但是** 重试 pending 的失焦仅隐藏，遵循请求结果暂存与原框聚焦恢复规则；失焦期间新到达的错误可在原框聚焦时展示

### Requirement: 切换语言重译必须提供中间状态

系统必须在同一个来源状态槽展示重译进度与错误，复用输入框 spinner，禁止在条体新增第二个 spinner。该需求同时修复 Bug #61290。

#### Scenario: 请求等待中

- **当** 用户选择另一种语言
- **则** 必须立即显示新选语言，禁用选择器，状态槽显示「翻译中…」，保留旧译文和可用撤销
- **且** 同一请求期间的重复选择与重试不得额外发起翻译请求

#### Scenario: 重译成功或失败

- **当** 请求成功且写回守卫满足
- **则** 必须以最初原文的译文替换输入，并将来源改为「手动选择」
- **当** 请求失败
- **则** 必须保留当前输入、原始快照及撤销，恢复上次成功语言与来源，按错误类别显示错误说明及可选重试
- **且** 点击重试必须将最初原文译为回退后当前显示的语言，而不是失败的请求语言

#### Scenario: 返回空结果

- **当** 引擎返回空字符串
- **则** 必须退出 pending，保持输入不变；已有成功条恢复上次成功语言与来源，不生成虚假成功译文

### Requirement: 请求结果不得覆盖已结束会话或新草稿

首次语言解析、首次翻译、重试与重译必须共用请求有效性规则；原文快照必须保存触发序列前用户输入的首尾空白，不得以规范化后的译文输入替代。

#### Scenario: 内联操作保持反馈和写回连续性

- **给定** 用户正在当前输入框、内联条或其专属语言菜单中操作
- **当** 用户选择语言或通过鼠标、键盘激活重试，菜单关闭或操作控件被禁用、移除
- **则** 必须在动作阶段将焦点交还原输入框，持续显示翻译中反馈；成功结果无需用户额外点击输入框即可写入
- **但是** 用户随后主动离开时不得抢回焦点，仍按失焦结果暂存规则处理

#### Scenario: 焦点交接中会话失效

- **当** 同步聚焦触发空草稿会话清理、会话替换、路由或草稿变化、元素卸载或其他请求启动
- **则** 必须终止旧动作，不再发布旧会话 pending、不发起旧会话请求或写入旧原文
- **但是** 仅因原框重新聚焦而更新显示状态不得阻止有效操作

#### Scenario: 请求期间撤销或结束会话

- **当** 用户撤销、在菜单关闭时按 Esc、实际发送消息、移除输入元素、切换路由或开启新会话
- **则** 旧请求的成功、失败与清理必须不得修改新会话或新请求；撤销必须立即恢复最初原文
- **且** 首次尚无内联条时也必须能够使旧请求失效

#### Scenario: 请求期间用户编辑或编辑后改回

- **当** 用户在 pending 期间编辑输入，即便随后改回相同文本
- **则** 必须放弃旧结果，不覆盖草稿；已有成功条恢复非 pending 的成功语言并继续保留最初原文撤销，首次请求不生成纠错条

#### Scenario: 触发空格之间粘贴或拖放

- **当** 用户在连续空格序列中通过粘贴、拖放、输入法或其他非空格编辑改变草稿
- **则** 必须重置触发计数和快照；下一段连续三空格保存新的完整原文，撤销不得丢失这些编辑

#### Scenario: 失焦时结果返回

- **当** 请求成功时焦点已离开原输入框及交互范围
- **则** 只暂存当前请求结果，不抢焦点写入；重新聚焦原框且请求、路由、草稿仍有效时才提交
- **且** 失焦不永久结束会话，暂存期间撤销与请求失效仍生效

### Requirement: 输入翻译控件统一适配输入区域主题

内联条、同语言提示和语言菜单必须使用同一套与宿主输入区域协调的深浅色配色。主题判断不得改变用户的扩展主题设置或其他 UI 入口，也不得触发翻译或写入输入框。

#### Scenario: Discord 主题与扩展主题不同

- **给定** Discord 使用深色主题而扩展使用浅色主题，或二者相反
- **当** 显示输入翻译内联条并展开语言菜单
- **则** 条体、语言名称、说明、撤销、搜索框和菜单列表必须统一适配 Discord 的主题
- **且** 同语言提示必须采用相同的主题策略

#### Scenario: 通过输入区域背景判断主题

- **给定** 页面没有可识别的站点主题标记
- **当** 输入区域背景为纯色或可结合祖先求得有效颜色的透明、半透明背景
- **则** 系统必须根据输入区域有效背景亮度选择深浅色主题

#### Scenario: 无法可靠判断主题时回退

- **给定** 背景包含图片、渐变或无法可靠计算有效颜色
- **当** 显示内联条或语言菜单
- **则** 系统必须回退扩展当前解析后的主题，并以不透明背景保证文字清晰

#### Scenario: 页面切换主题时保留当前交互

- **给定** 内联条正在显示或语言菜单已展开
- **当** 用户切换页面的深浅色主题
- **则** 条体与菜单必须同步更新配色，保持焦点、菜单开关状态、搜索文本、已选语言及原文快照
- **且** 不得因此重译、关闭会话或写入用户草稿；失焦隐藏后重新聚焦也必须使用最新主题

#### Scenario: 主题适配隔离与清理

- **当** 输入翻译应用局部主题，随后原输入元素替换或卸载
- **则** 设置页、划词浮窗及用户持久化主题偏好必须保持原行为，旧元素的主题监听及专属 Portal 容器必须正确清理
- **且** 主题检测不得依赖对整页消息子树的全量监听或持续轮询

### Requirement: 内联条与语言菜单清晰可读且适应可用空间

普通文字（含说明、搜索占位和撤销）与实际背景对比度必须至少为 4.5:1。语言选择和撤销必须具备清晰的键盘焦点及悬停反馈，语言菜单必须提供可辨识的选中状态。

#### Scenario: 深浅主题下的文字与操作反馈

- **当** 用户查看内联条、同语言提示或语言菜单，或通过鼠标、键盘操作
- **则** 两种主题的文字对比度都必须达标，撤销不得呈现禁用外观，焦点轮廓及菜单悬停、选中状态必须可辨识

#### Scenario: 语言菜单向上展开与窄视口

- **当** 用户展开语言菜单，包含长语言名称或可用空间不足
- **则** 菜单必须向上展开，常规宽度约 220–320px，并受视口可用宽度约束；上方空间不足时缩小高度、在列表内部滚动
- **且** 长语言名称允许合理换行，不遮盖选中勾选、不产生横向溢出；语言排序与选择语义保持不变

#### Scenario: 菜单主题作用域不改变生命周期

- **给定** 菜单使用输入翻译专属 Portal 容器
- **当** 用户操作菜单、按 Esc 或移开后重新聚焦原输入框
- **则** 必须继续满足既有的交互范围判断、分层 Esc、失焦恢复、原文重译及撤销要求
